- `package-lock.json` plus pauvre que `package.json` (`babylonjs-gltf2interface@5.57.1` retirée) → `npm ci` dans le Dockerfile peut échouer au prochain build.

**Verdict** : le lot est **cohérent et bien branché** (compose ↔ gateway ↔ agent-team ↔ microservice ↔ frontend, les endpoints vérifiés existent tous). Il ne manque que le commit, le `chown`, et le câblage dans les 4 scripts.

### 3.3 Vulnérabilités détaillées

#### 🔴 CRITIQUE — Prise de contrôle d'agent via OAuth

`OAuthSocialController.java:140-154` + `:348-407`, avec `SecurityConfig.java:36` en `permitAll`.

```
1. GET /api/oauth/social/{platform}/authorize?agentId=X     → public
2. @AuthenticationPrincipal est null
   → effectiveUserId = agentRepo.findById(X).ownerId          (ligne 149)
   = l'identité du PROPRIÉTAIRE de l'agent choisi par le visiteur
3. state = "<userIdPropriétaire>:<agentId>[:channelId]"      (ligne 153)
4. l'attaquant fait le flux OAuth avec SON compte Facebook
5. handleOAuthCallback ne ré-authentifie personne             (ligne 348)
   → userId est lu DU STATE (ligne 365)
6. échange du code de l'ATTAQUANT                            (ligne 372)
7. createChannel(userId=VICTIME, agentId, credentials=ATTAQUANT)  (ligne 402)
   → resolveAgent() passe la vérification de propriété         (ChannelService:151)
   → statut CONNECTED
```

**Confused deputy** : l'agent de la victime publiera/commentera désormais sur les pages de l'attaquant. Et comme le contrôle de propriété est satisfait avec l'identité de la victime, `ChannelService.resolveAgent` **ne peut pas** le détecter.

Second problème : le chemin de mise à jour (lignes 377-390) est plus faible encore — `channelRepo.findById(channelId).filter(c -> c.getAgent().getId().equals(agentId))` ne vérifie que l'agent, contourne `ChannelService.updateChannel`, et `c.getAgent()` peut NPE.

#### 🔴 CRITIQUE — Secret JWT par défaut, identique dans 5 services

| Fichier | Défaut |
|---|---|
| `api-gateway/application.yml:328` | `${JWT_SECRET:<littéral-en-clair>}` — défaut identique dans les 4 autres services |
| `auth-service/application.yml:39` | idem |
| `agent-team-service/application.yml:99` | idem |
| `generation-service/application.yml:68` | idem |

Avec ces valeurs : **forge de jeton pour n'importe quel `sub` (email)**. `agent-team` et `telegram-mcp` l'acceptent. L'écart entre `telegram-mcp` et les 4 autres provoque en prime un rejet mutuel des jetons si `JWT_SECRET` n'est pas défini.

#### 🟠 HAUTE — Upload public (introduit par le diff non commité)

Deux maillons :

1. **Gateway** — la route `media-upload` (`/api/media/**`) n'a qu'un `RewritePath`, pas d'`AuthenticationFilter`. Sur ~37 routes, **seules 7 en ont un** ; 30 sont ouvertes, dont `/api/media/**`, `/api/oauth/social/**`, `/api/ocr/**`, `/api/agents/**`, `/api/facebook/**`, `/api/user/credentials/**`.

#### 🟠 HAUTE — Scan antivirus fail-open à trois endroits

```java
boolean safe = result.path("safe").asBoolean(true);   // défaut = true
```

- service répond 200 avec un JSON sans champ `safe` → traité comme **sûr**
- seul `HttpStatus.OK` est interprété : un 201/204 ou autre 2xx **saute** tout le verdict
- `catch (Exception e)` log un warning et **poursuit vers MinIO** — le commentaire est auto-contradictoire : *« fail-open ou fail-closed selon politique »*

Aggravants : les `MAX_IMAGE_SIZE_MB`/`MAX_VIDEO_SIZE_MB`/`MAX_DOC_SIZE_MB` sont injectés dans l'env du scanner mais **jamais lus** par `main.py` → le chemin fail-open n'a **aucune** limite de taille. `file.getBytes()` charge le fichier entier en heap, deux fois. `new RestTemplate()` **sans timeout**. `file-security-service` n'a **aucune limite de streaming** non plus (`await file.read()`).

Le gateway autorise 210 Mo. → **DoS mémoire trivial**.

### 5.3 Les 5 problèmes qui comptent

### 6.1 Les 5 problèmes qui cassent en production

#### 1. 15/35 services sans politique `restart`

Dont **`postgres`**, **`redpanda`**, **`minio`** et les **7 workers IA**. Après un reboot du VPS : base de données et tout le pipeline de reconnaissance **éteints**. `start.sh stop` ne les relance pas.

#### 2. `control_server.py` sur `0.0.0.0:8490`, sans authentification, CORS `*`


→ **n'importe quel site web peut piloter le stack Docker** depuis le navigateur d'un visiteur, et l执行 est en `subprocess.Popen` **sans `wait()` ni capture de sortie** (les erreurs sont invisibles).

#### 3. 28/35 services sans healthcheck

Seuls 7 en ont un : `postgres`, `redis`, `redpanda`, `ollama` (**cassé**), `video-generation-worker`, `image-generation-worker`, `file-security-service`.

#### 4. 3 routes gateway pointent sur `localhost`

`api-gateway/application.yml:82, 90, 98` :

Le bloc `environment` du compose (`:134-142`) ne définit **ni `AUDIO_AI_HOST`, ni `VIDEO_AI_HOST`, ni `FACE_AI_HOST`** → les 3 routes `/api/ai/{audio,video,face}/**` pointent sur le **localhost du conteneur gateway** → connexion refusée.
